# ArchiMate Browser: improvements and to-dos

Prototype status and next steps. IDs (e.g. `BR-3`) are for referencing in
discussions and commits. Priorities: **P1** next iteration, **P2** soon,
**P3** nice to have.

## 1. Observations about ArchiMateAPI (resolved by API v2)

> **Resolved.** Everything observed against API v1 is resolved by the API
> (2.0.0 to 3.6.0) and adopted by the browser in the five phases of
> [PLAN.md](PLAN.md), finished on 2026-10-24 (2.9.0). API-12 was dropped by
> decision. The specification is
> [API_IMPROVEMENTS.md](../ArchiMateAPI/API_IMPROVEMENTS.md) (API-1 – API-12, HLP-0 –
> HLP-10) and [API_IMPROVEMENTS_2.md](../ArchiMateAPI/API_IMPROVEMENTS_2.md) (HLP-11,
> HLP-12), in the API's folder. Kept here as the record.

| ID | Observed against API v1 | Now |
| --- | --- | --- |
| API-1 | Spec says `limit` up to 1000, the API refused more than 200. | Pages of 1000. |
| API-2 | View connections came as a bare array, without the paged envelope. | Every list has `{ items, total, limit, offset }`; a view in one request (`…/content`). |
| API-3 | No CORS. | `CORS_ORIGINS` in the API; the browser can run without the proxy (README, *Running without the proxy*). `serve.py` stays the default. |
| API-4 | No "views that show element X". | `…/elements/{id}/views`, `…/relationships/{id}/views`. |
| API-5 | No counts per type. | `…/stats`: the tree, the status line and the details. |
| API-6 | One capped search list, no paging per kind, no filters. | `…/search` with a page per kind and property filters. |
| API-7 | `localhost` costs about 2 s per request on Windows. | The API's `python -m app` listens on `127.0.0.1` and `::1`; the proxy keeps `127.0.0.1` as its default, which is fast with every way of running the API (README). |
| API-8 | One shared key with full write access. | Several keys with roles; the browser asks what its key may do (`/auth/me`). |
| API-9 | View connections could not end on a connection. | They can; drawn in views. |
| API-10 | No "views that link to view X". | `…/views/{id}/links`. |
| API-11 | Folder items could not reference views. | `refViewId`: views in folders. |
| API-12 | Text position and alignment of nodes are not in the exchange format. | Dropped by decision; labels stay centred. |

### 1a. API helpers (graph and query helpers): resolved

The browser used to load the **whole model** and compute these itself. All
of them are now answered by the API, and the browser loads a model on
demand (phase 4): no code in `js/` walks the relationships of the model.

| ID | What the browser computed itself | Now, from the API |
| --- | --- | --- |
| HLP-0 | Nothing could be cached. | Model revision, `ETag` / `If-None-Match`, also for the POST helpers (`ask()` in `js/api.js`). |
| HLP-1 | Neighbourhoods, walking the loaded graph. | `POST …/graph/neighbourhood`, with filters, nesting and the hidden counts. |
| HLP-2 | Relationships among a set, nesting. | `POST …/graph/subgraph`. |
| HLP-3 | Impact analysis and its CSV. | `POST …/graph/impact` (JSON or CSV). |
| HLP-4 | (not possible) Paths between two elements. | `GET …/graph/paths`. |
| HLP-5 | The explorer's "+N" and its per-type menu. | `POST …/graph/expansion-counts`. |
| HLP-6 | The tree's `n↗ m↙`. | `include=degree`. |
| HLP-7 | Folder counts, contents, paths; a view's elements. | `counts=true`, `…/contents`, `…/{kind}/{id}/folder`, `…/views/{id}/elements?positions=true`. |
| HLP-8 | Everything was loaded, as single items could not be fetched. | `ids=` on the lists: the browser's cache (`ModelStore.ensure`). |
| HLP-9 | Property index and filters. | `…/properties/index`, property filters on lists, search and helpers. |
| HLP-10 – HLP-12 | (not available) Quality report, relationship matrix, landscape map. | `…/analysis/quality`, `POST …/graph/matrix`, `POST …/graph/hierarchy`: the *Reports* (2.8.0). |

## Appendix A: Several diagrams open at once (BR-15)

Analysis of internal diagram tabs. Verdict: feasible, a **medium refactor**
rather than a UI addition, because the app assumes exactly one diagram.

### What stands in the way

All diagram state is global in `app.js`: `state.diagram`, `diagramDef`,
`layout`, `gen` (manual layout and undo), `exploreBack`, `info` and
`highlight`. These are referenced about 125 times. One `#tab-layout`
element holds the drawing, and one PlantUML panel and one Source panel hold
the rest.

| Coupling | Problem with several tabs | Fix |
| --- | --- | --- |
| Global diagram state | Every action reads `state.gen` and similar fields. | Group them into a **document** object, `state.doc`. To keep the change small, the old field names can become getters that read the active document. |
| Async rendering (ELK layout, view loading, PlantUML) | `layoutSeq` and `renderSeq` throw away a result once anything newer starts. With tabs, a layout that finishes after you switch tabs must still land in its own tab. | Capture the target document when work starts and draw into it; keep one sequence number per document. This is the main real work. |
| One drawing container | Switching tabs would re-run ELK and lose zoom, undo, highlights and explorer history. | Give each tab its own container and hide the inactive ones. The SVG stays alive, so switching is instant. |
| Filters, property options and layout options are global | A background tab drawn under different filters would be stale. | **Per tab.** Diagram links already carry `f=`, `p=` and `lo=` per diagram. The panels show and edit the active tab's values; a new tab copies the current ones. |
| The URL hash describes one diagram | Not enough to share every open tab. | The hash stays the **active** tab, so links still share one diagram. The list of open tabs goes in `sessionStorage` and is restored on reload. |
| Manual layouts are keyed by the diagram definition | Two tabs with the same definition share stored positions. | Acceptable: identical content gets an identical arrangement. Undo stays per tab. |

No change needed:

* Details pane, tree and basket.
* The multi-selection (CM-6), which is global and works across tabs.
* The toolbar, which acts on the active tab.
* The minimap, which is already created per drawing.

### How it would behave

* **Tab bar** above the diagram:
  * Each tab shows its title, a close ×, and a dot when it has unsaved
    manual moves.
  * Middle-click closes a tab; a **+** button opens an empty diagram.
  * Right-click a tab: *Duplicate*, *Close others*, *Copy link*.
* **Opening diagrams:** by default as today, replacing the active tab.
  *Open in new tab* appears in every menu that leads to a diagram, and
  Ctrl- or middle-click on those buttons and items does the same. This also
  covers CM-12.
  * Optional preview tabs (as in VS Code): an untouched generated tab gets
    replaced; it becomes permanent once you move, expand or hide something
    in it.
* **Limits:** around 15 tabs. Only the ~5 most recently used keep their
  live drawing; the others keep just their definition and re-render when
  activated. Manual positions are stored, so they come back the same; zoom
  and undo history are lost for those tabs.
* **Across tabs:** drop elements, folders, views or the basket onto a tab's
  title to add them there. The selection menu could get *Add to diagram in
  tab…*.

### Phases

| Phase | Content | Size |
| --- | --- | --- |
| 1 | Document model and per-document async rendering. No visible change, but every render path needs retesting. Worth doing on its own: it removes the race conditions of the global rendering state. | M (risky) |
| 2 | Tab bar, *Open in new tab*, restore open tabs on reload. | M |
| 3 | Per-tab filters, property options and layout options. | S–M |
| 4 | Drag onto tab titles, memory cap, preview tabs. Each optional. | S |

Recommendation: phases 1–3.

**Status (2026-10-24):** phases 1 to 3 are done (2.11.0). Where the result
differs from the design: the tab bar is shown only with two or more tabs;
*in a new tab* is a Ctrl- or middle-click on menu entries and on the buttons
of the details pane (rows of the tree keep Ctrl-click for selecting several),
plus explicit entries for a view, *Duplicate in a new tab* and *New empty
tab*; no unsaved-changes dot, since manual layouts are saved at once. Phase 4
is open.

### Cheaper alternatives

* **Recent diagrams list:** a dropdown that re-renders a past diagram from
  its definition. About a day of work, no refactor, but nothing stays alive
  in memory.
* **Open in new browser tab (CM-12):** each browser tab already runs on its
  own. The catch: a filter changed in one browser tab is saved as the
  default for the next render in the others.
